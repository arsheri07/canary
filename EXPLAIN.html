Canary — how to explain it

~240 lines of real logic · read once, then talk normally
You need to read two files: scanner.py (~100 lines) and detect.py (~137 lines). That's it. canary.py is just printing and argument handling — skim it.

The 30-second version

say this

"It watches a folder and tells you what changed. The useful part is that it can tell the difference between you editing a file and ransomware encrypting it."

"Encrypted data looks random. Random data has high entropy. So if a document's entropy jumps from 4 to 8, it wasn't edited — it was encrypted."

"File integrity monitoring is actually a required control under PCI-DSS. Tripwire and OSSEC are the commercial versions. I built a small one to understand how it works."

How it works — three steps

  1. Fingerprint every file. SHA-256 hash of the contents. Change one byte and the hash changes completely, so if the hash is the same, the file is identical.
  2. Compare to last time. Three set operations tell you everything: what's new, what's gone, and what's still there but has a different hash.
  3. Decide what it means. 40 files changing could be a build, or an attack. Six signals score it.

The entropy part (the only "clever" bit)

Entropy = how unpredictable the bytes are, on a 0 to 8 scale.

English text      4.4    lots of 'e' and spaces, very predictable
Encrypted data    7.98   every byte value equally likely, no pattern
All zeros         0.0    completely predictable

Those are numbers measured from the actual code, not theory. Encryption is designed to look like noise — that's what makes it secure — which is exactly what gives it away.

if they ask how entropy works

"It's a formula that measures how surprising the next byte is. In English text you can guess pretty well — it's probably an 'e' or a space. In encrypted data every byte is equally likely, so you can't guess at all. That's high entropy."

Don't recite the formula unless asked. If they do ask: H = -sum(p × log2(p)), where p is each byte value's share of the total. It maxes at 8 because a byte is 8 bits.

Why six signals instead of one

Any single signal has a legitimate explanation. Lots of files changed? That's a build. High entropy? That's a zip file. Together, though, almost nothing legitimate does all of them at once.

SignalPtsWhy it fires
50+ files modified30People edit a few. Ransomware does hundreds.
Entropy jumped40Contents now look encrypted
Known bad extension35.locked, .crypt, .ryuk
Ransom note appeared20HOW_TO_DECRYPT.txt
Mass delete + mass create25Encrypt-and-replace pattern
New files high entropy30The replacements look encrypted

70+ is CRITICAL. Below 20 is normal.

Your bug story (they will ask for one)

say this

"My first version scored encrypt-and-rename lower than encrypt-in-place — 60 versus 70. That's backwards, because renaming is the more common attack."

"The reason: renaming a file shows up as one 'added' and one 'deleted' entry, never 'modified'. Both of my entropy checks only looked at modified files, so the encrypted content landed somewhere nothing was watching."

"Nothing crashed. The code ran fine the whole time and just quietly under-scored the most common real attack. I only caught it because I wrote a test comparing the two cases side by side."

That's a strong answer because it's about testing an assumption, not fixing a crash.

Questions you'll get

"Doesn't a firewall already do this?"

No — a firewall watches network traffic and has no view of your filesystem. Ransomware from an email attachment crosses no firewall, and encrypting your own files generates no network traffic at all.

"Doesn't antivirus do this?"

Antivirus is mostly signature-based — it recognizes known-bad files. New ransomware has no signature yet. Canary doesn't care what the malware is; it notices that files just became statistically random. New ransomware still has to encrypt, and encryption always raises entropy.

The line: "Defense in depth. Firewall watches the network, antivirus watches for known-bad files, FIM watches for unexpected change. That's why PCI-DSS requires FIM as a separate control."

"Isn't this already a solved problem?"

Yes — Tripwire, OSSEC, Wazuh, AIDE. Say that plainly. "It's a standard control; I built a small version to understand it." Claiming novelty in a mature category makes you look like you don't know the field.

The narrow honest claim: adding entropy analysis is less common in simple implementations, and it's what catches in-place encryption where filenames never change.

"Why SHA-256 and not MD5?"

MD5 is faster but broken — you can compute two different files with the same MD5. An attacker could swap a file without the hash moving, which is exactly the attack this tool exists to catch.

"What would you do differently?"

It polls on a timer instead of using filesystem events (inotify/FSEvents), so detection is delayed by the interval. And the baseline file isn't signed — malware with write access could tamper with it.

Prove it works, in 60 seconds

mkdir /tmp/demo && cd /tmp/demo
for i in $(seq 1 30); do echo "document text here" > doc$i.txt; done
python3 ~/canary/canary.py baseline /tmp/demo

# simulate ransomware
python3 -c "
import os,secrets
for f in os.listdir('/tmp/demo'):
    p='/tmp/demo/'+f
    open(p,'wb').write(secrets.token_bytes(2048))
    os.rename(p,p+'.locked')"

python3 ~/canary/canary.py check /tmp/demo
# -> RISK: CRITICAL 90/100
